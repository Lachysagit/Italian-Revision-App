Level 1 Data Flow Diagram

The Italian oral exam simulator, generalised from its source into seven major processes. Every element below was traced through the running code rather than the prose in the README.

The diagram

Circle: a process. Open‑ended rectangle: a data store. Closed rectangle: an external entity. Labelled curved arrow: a data flow. Dashed grey marks a flow that is planned, or that carries control rather than data.

External entities

The system boundary encloses both the browser client and the C++ server, because web/client.js is this project's own code served by its own route. The student — their voice and their ears — is what sits outside it.

IDEntityWhy it is outside the boundary
E1StudentHuman source of speech and sink of audio and text. Reached through getUserMedia and the audio destination node.
E2Gemini APIThird‑party service called over HTTPS, with the API key sent as an x-goog-api-key header.
E3Piper voice engineA separate operating‑system process, spawned and talked to over pipes — not a linked library.
E4Ollama server plannedWould be a local HTTP service for the Hailo examiner backend. The class exists and returns a placeholder.
E5Host machineStartup only. Supplies the CPU count when WORKER_THREADS is unset. The server's machine, not the student's.

Whisper is deliberately not an entity: it is linked into the server and called in‑process, so it lives inside process 4. Piper genuinely is a subprocess. That asymmetry is real — don't tidy it into symmetry.

Major processes

Fifteen code‑level transformations generalised into seven. Process 0 runs once at startup and is drawn separately so it does not clutter the turn cycle.

IDProcessGeneralises
1Capture student speechMicrophone capture, turn trimming, downsample to 16 kHz, float32 → int16, transmit.
2Assemble utteranceBinary frame reassembly, odd‑byte carry between frames, buffer cap at 40 seconds.
3Manage exam turnParse control JSON, route start/stop, claim the session, snapshot the history, dispatch to a worker thread.
4Transcribe speechWhisper inference over the utterance, producing trimmed Italian text.
5Generate examiner replyBuild the request from the history, call the model, parse the candidate reply.
6Synthesise reply speechReply text to Piper's stdin, raw int16 PCM back off stdout.
7Deliver turn to studentSerialise frames, render turn cards, play back the audio, re‑arm the microphone.
0Initialise systemRead environment into Config, construct the three backends, load the system prompt. Startup only.

Data stores

There is no database and no file the running server writes. Every store except the model files, the prompt and .env lives in memory and dies with the process; the per‑connection ones die with the WebSocket.

IDStoreHolds
D1Utterance bufferThe current turn's PCM, plus the odd carry byte left between binary frames.
D2Conversation stateSystem prompt, last question, last answer — the examiner's entire memory of the exam.
D3Job queuePipeline jobs waiting for a worker thread.
D5aWhisper model fileGGML weights, loaded once at construction.
D5bPiper voice + configONNX voice weights, and the sample rate read from the voice's JSON sidecar.
D6.env fileConfiguration at rest. Read at startup only — never during a turn.
D8Examiner system promptRead once at startup, copied into every new session.

Two more exist in the code but are not stores on this diagram. The session registry is a lookup table, not data the system reads back as content. job_in_flight_ is a control flag — it belongs on the structure chart as a control couple. A declared fact_store_ is never read or written anywhere, so it has no flows at all.

Choices worth defending

The browser is inside the boundary

If you would rather draw it as external, processes 1 and 7 collapse into E1 and their flows disappear. Either convention is defensible — say on the diagram which one you used.

Configuration is a startup concern

Config is a value built once and consumed to construct objects, not data at rest that a process reads back. Only two of its fields become real flows: the API key, carried on every request to E2, and the Piper sample rate, which reaches the student's browser inside the reply frame.

Thread count and port are not on the diagram

They change how fast the queue drains and where the student connects, but never appear in any payload. Resourcing belongs in the written documentation, not on an arrow.

Nothing flows from the student into configuration

There is no route, no setter, and inbound parsing only ever produces a message. Nothing a student sends can change how the server is configured — that absence is a property worth stating, not an omission.
